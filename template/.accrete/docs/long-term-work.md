# Accumulating useful work

ACCRETE is most useful when the next session can begin from the code, products,
capabilities, and understanding that earlier work made available. Retention is a
selective act of project judgment. It can happen during work or after its value
becomes apparent.

## Preserve the right distinction

| What is changing | Suitable durable description | What stays native |
|---|---|---|
| A numerical program develops | Model identity and meaningful iteration outcomes | Repository commits, branches, builds, and execution |
| A diagnostic becomes worth reusing | Tool purpose, source, and exposure | Scripts, compiled code, examples, and domain explanation |
| A product is selected for future use | Data meaning, origin, content description, and locations | Native scientific files and storage |
| An activity produces observations | Result with the operands and context actually known | Detailed logs, traces, arrays, and external tracking systems |
| Understanding changes | Memory explaining the interpretation and its conditions | Authored reasoning and native text search |

These can occur at different times. An experiment can run before its Result is
recorded. A script may remain temporary until a later task reveals a recurring
purpose. A new interpretation can be written long after the original run. No
single object needs to carry all of those changes.

## Continue from prior work

Read the relevant Result and Memory before deciding whether further execution is
useful. The observations describe the code, Tools, Data, and conditions they
name. Preserve them when a Model advances; their historical context remains
meaningful.

A changed project commit may concern documentation only. A changed comparator or
mapping can affect an interpretation even when the Model is unchanged. The
Agent and domain Tools decide what matters to reuse. ACCRETE has no universal
rule equating commit equality with scientific equivalence or commit difference
with a required rerun.

When further work is justified, name the uncertainty it resolves. It might be a
new mechanism question, a changed operand, a missing product, or a new computing
environment. The useful Result then explains the actual activity and its
observations without pretending it speaks for unrelated revisions or conditions.

## Let capability grow through practice

Keep a one-off analysis script in ordinary source or Scratch while it is still
being developed. When it has a recurring purpose, retain the code and the
knowledge required to use it. The Tool may contain scripts, compiled programs,
reference material, or prose alone. Admit it through the Kernel when it should
have a project identity.

A Skill is one discovery interface for that capability. Expose it when automatic
discovery helps. It can also be used directly by path or by another program.
Keep the Tool's editable source distinct from generated host wrappers. Refresh
the exposure when its description or binding changes; code edits still happen
with normal development tools.

Record the implementation used for a particular activity when known. An
admission-time commit on a live Tool does not automatically identify the code a
later run executed. Selecting a retained revision requires actual matching
material; a label alone cannot freeze a mutable directory.

## Keep knowledge understandable

Useful Memory explains how an observation changed the understanding of a
problem, why a choice was made, which conditions limit it, and what could help
next. Write in normal prose. Do not turn every command, transcript, or transient
machine observation into a Memory entry.

If a later explanation changes, append a new entry linking the earlier one and
the relevant Results. Explain what changed and why. Preserve the earlier
interpretation in the conditions in which it was made. Dated Markdown and stable
IDs provide continuity without controlling the style of the explanation.

As a topic becomes difficult to navigate, author a useful synthesis and link its
supporting entries and Results. A Tool can contain a durable method distilled
from several such experiences. The project does not require an automatic
summarizer, embedding index, or scoring system before it can benefit from Memory.

## Retain meaning without copying every byte

Data registration can describe a large remote product in place. Keep compact
diagnostics or reduced tables close to analysis while preserving the locations
of raw outputs or restart states that are worth retaining. Content digests,
provider versions, and manifests have their own scopes; use what is known and
worth computing for the task.

Two products with identical bytes can have different scientific roles. Preserve
both meanings. A corrected closed product normally receives a new identity or
an explicit content version so old Results continue to refer to the input or
output they actually used.

Retaining a descriptor does not ensure that a remote path will remain available.
Use the storage service's actual conditions and the owner's retention choices.
Before removing working storage, identify the selected material that subsequent
work needs and preserve it through ordinary source retention, Data locations,
or an explicitly chosen archive.

## Separate project progress from software upgrades

The Kernel, foundational guidance, Model, Tool, Data, and Memory evolve on their
own schedules. A distribution upgrade makes a different executable available.
A project upgrade updates compatible foundational assets. A migration changes
managed document representation. Neither action advances a Model, revises an
earlier interpretation, or declares a scientific result obsolete.

Use [the configuration guide](configuration.md) to resolve the active host and
[the remote guide](remote-work.md) when computation and analysis happen in
different environments. Preserve the relationships that help the next action;
let the research continue in the form appropriate to its question.
